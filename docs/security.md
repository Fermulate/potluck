# Security

How Potluck protects its data, what it stores, and where the known weak spots are. To report a vulnerability, follow [SECURITY.md](../SECURITY.md). The mechanics (grants, RLS, definer RPCs, storage policies, edge function auth) are in [architecture.md](architecture.md#security-model).

## Threat model

### What is worth protecting

- **Money history.** Who paid whom, how much, and when. Tampering with it moves real debts between friends.
- **The social graph.** Who is in which group, who is friends with whom, who blocked whom.
- **Plans.** Availability grids and event locations say where people will be and when.
- **Receipts.** Photos can carry addresses, card digits and location metadata.
- **Account data.** Email addresses and display names.

### Known gaps

These are real today. Each should become an issue.

- **Closed accounts keep their calendar feed.** `delete_my_account()` does not delete the `calendar_feed_tokens` row, and `ics-feed` does not check `profiles.deleted_at`. A closed account that still has an open balance in a group keeps that group's membership, so its old feed URL keeps listing that group's events.
- **Avatar files outlive the account.** The profile's `avatar_path` is cleared, but the file stays in the public `avatars` bucket, at a URL anyone who saw it can still open.
- **Admin invite rule mismatch.** `can()` in core lets admins create admin invites. The server refuses, so this is a UI bug, not a hole.
- **Previews use production data.** PR preview builds point at the production Supabase project. Anyone who can open a PR that gets a preview deploy can ship code that runs against real accounts. Today previews only build for branches in this repository, because fork PRs do not get the Cloudflare secret.
- **Edge function CORS is `*`.** Harmless for the secret- and token-protected functions, and `delete-account` requires a JWT, but it is wider than the app needs.
- **Invite previews show first names** to anyone with the code. That is the point of the join page, but it means an invite link is a small leak of who is in the group. A claim link also shows the saved seat's first name and its masked email.
- **A placeholder's name and masked email are visible to its group.** The full address is readable by no client; the person who typed it in knows it.
- **Guest links are open doors until they close.** Anyone with the code can add names and times up to the link's cap, and the per link limits (20 new guests per 10 minutes, 60 saves per guest per hour) are counted in the database, not per IP. Organizers clean up with remove and turn off. The preview itself is a read and is not rate limited.
- **Signing out elsewhere is not instant.** "Sign out everywhere" and a password change revoke every other refresh token, but an access token already handed out keeps working until it expires (up to an hour, `jwt_expiry`).
- **A fresh stolen session can change the password without the old one.** Within a day of signing in, Supabase sets a new password for the session alone; the Me page asks for the current password first, but the API does not unless the project turns on "require current password" (a dashboard setting, not in `config.toml`; the app already sends `current_password`). Older sessions need an emailed code (`secure_password_change`). Either way the account gets a "password changed" email.
- **A half signed in session can edit its own user metadata.** Supabase Auth allows it at `aal1` and the database never sees that write. Nothing there grants access (see ADR 13).

## Sign in

- **Methods.** Email and password, a magic link, and Google or Apple once their flags are on. Production requires a confirmed email before the first sign in.
- **Two-step sign in.** An authenticator app (TOTP) from the Me page. Signing in with any method then asks for a code. The database enforces it ([ADR 13](adr/0013-two-step-sign-in-enforced-in-the-database.md)): until the code is in, every REST and RPC call fails with `mfa_required`, Storage reads and writes nothing in any bucket, and Realtime sends nothing. Supabase Auth refuses that session's email, password and factor changes. Turning it off needs a fresh code.
- **Recovery codes.** Ten one-time codes are shown once at setup (and again whenever they are replaced); the dialog only closes once the person says they saved them. They are stored as SHA-256 hashes, which is enough because they are random. One code, together with the first sign in step, removes the authenticator so the person can set it up again. Five tries per account per fifteen minutes, then `too_many_attempts`. Turning two-step sign in off clears them. Without the codes, an operator has to remove the factor by hand after checking who is asking.
- **Changing the email** sends a link to the old and to the new address (`double_confirm_changes`); in production the switch happens only when both are opened, so a stolen session cannot quietly move the account to another inbox. (The local stack auto-confirms email, and Supabase then takes either link as enough.) A pending change can be called off from Me (`cancel-email-change`), which voids its links.
- **Changing the password** asks for the current one (accounts that only ever used Google or Apple set a first password without it), and for an emailed code when the session is more than a day old (`secure_password_change`). Then every other session is signed out.
- **Security emails.** Supabase emails the account when its password or email changes and when an authenticator is added or removed (`[auth.email.notification.*]`). A recovery code removes the authenticator with the admin API, which sends no email, so `mfa-recover` files an `account.mfa_removed` notice instead: inbox and push right away, email through the app's outbox once email notifications are on. Its `security` category is required: it has no setting, `set_notification_pref` refuses it, unsubscribe links (one category or all) leave it on, and these emails carry no unsubscribe links or headers.
- **Sign out everywhere** revokes every session of the account, this one included.

## Data handling

### What is stored

| Data                                                      | Where                                            | Visible to                                                                                                                                               |
| --------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email, password hash, sessions                            | `auth.users` (Supabase Auth)                     | nobody through the API. Supabase operators                                                                                                               |
| Display name, avatar, time zone, locale, default currency | `profiles`                                       | you, people you share a group with or who left one of your groups, friends                                                                               |
| Groups, members, invites                                  | `groups`, `group_members`, `group_invites`       | members. Invites only to admins and the invite's creator                                                                                                 |
| People not on Potluck yet: name, invite email             | `profiles`, `placeholders`                       | members of that group (the email masked); the address is used only for their invite and reminder, and deleted when they claim the seat or the group goes |
| Friend links                                              | `friend_invites`                                 | only you                                                                                                                                                 |
| Blocks, reports                                           | `blocks`, `reports`                              | only you (the Potluck team reads reports)                                                                                                                |
| Expenses, splits, settlements, comments                   | money tables, `comments`                         | members of that group                                                                                                                                    |
| Availability, RSVPs, events                               | plans tables                                     | members of that group                                                                                                                                    |
| Guest names and times                                     | `event_guests`, `event_guest_availability`       | members of that group. Guests see only counts per slot, never names. The guest's token is stored as a sha256 hash nobody can read                        |
| Busy blocks, calendar links                               | `busy_blocks`, `calendar_connections`            | only you. OAuth tokens would live in Vault (feature is off)                                                                                              |
| Notifications, push subscriptions                         | `notifications`, `push_tokens`                   | only you                                                                                                                                                 |
| Notification settings                                     | `notification_prefs`                             | only you                                                                                                                                                 |
| Receipts                                                  | private `receipts` bucket                        | members of the group (authenticated download or signed URL)                                                                                              |
| Avatars, group covers                                     | public buckets                                   | anyone with the URL                                                                                                                                      |
| Authenticator secrets, recovery code hashes               | `auth.mfa_factors`, `private.mfa_recovery_codes` | nobody through the API. Supabase operators                                                                                                               |

There is no analytics or tracking code in the app.

### What leaves the system

- **Push messages** go through the browser vendor's push service (Google, Mozilla, Apple). Web push payloads are encrypted for the subscribing browser, so the service cannot read the title and body, which may include an expense description or a comment.
- **FX sync** sends nothing about users to Frankfurter. It requests public reference rates.
- **Exports and backups** (Me, Your data; group settings) are built in the browser and saved to the person's device; nothing is sent elsewhere. `export_my_data()` returns only groups the caller is in now, with the names of everyone those groups mention, and the caller's own sign in email; anon cannot call it. Imports run as the importing member with every check `create_expense_v2` makes ([ADR 13](adr/0013-export-backup-and-import.md)).
- **Calendar feeds** contain event titles, descriptions, locations and group names for whoever has the URL.
- **Auth emails** go out through Supabase's SMTP.
- **Notification emails** (off until `app_config.email_notifications` is on) go through the configured provider (Resend). They carry the recipient's address, names, amounts and comment excerpts, so the provider can read them. That includes invites to people who are not on Potluck yet, sent to the address a group mate typed in.
- **Friend invites by email** are not sent by Potluck: the app opens the inviter's own mail app with the link.

## Account deletion

Users close their account from the app, which calls the `delete-account` edge function with their JWT. The flow is drawn in [sequences.md](sequences.md#delete-an-account).

What is removed: push subscriptions, calendar links, busy blocks, notifications, availability, availability requests, RSVPs, friendships, blocks, and memberships in groups where the balance is zero. Open invites the user created are revoked, except the claim links of seats they added, which stay usable. Groups they owned pass to the longest-standing admin, else the longest-standing member, and are deleted if nobody else is left. The auth user is soft deleted, so the email can no longer sign in.

What stays, and why: the profile row stays as a tombstone named "Former member" with no avatar, because other people's expenses and settlements reference it and their balances must not change. Memberships with an open balance stay so nobody's debt disappears. Expenses, splits, settlements, comments and activity the user took part in stay in their groups.

Closed accounts get `account_deleted` from every RPC and never receive notifications.

## Secrets policy

- **Never commit secrets.** `.env` and `.env.*` are git-ignored (except `.env.example`, which holds no values). The PR template asks every author to check.
- **The publishable key is public.** It ships in the web bundle and in `VITE_*` variables. That is fine, because RLS and grants decide what it can do. Never rely on it being secret.
- **The service role key never leaves Supabase.** Only edge functions use it, through `_shared/admin.ts`, and only after they have authorized the caller. It is never in GitHub, in `.env` files or in the web app.
- **`EDGE_SECRET` lives in two places**: the edge function secrets and the Vault entry `edge_secret`. Rotate both together ([deployment.md](deployment.md#vault-entries)).
- **`RESEND_API_KEY`** is an edge function secret only. Without it no notification email is sent.
- **The unsubscribe signing key** is generated by a migration into `private.signing_keys` and never leaves the database. Replacing that row breaks every unsubscribe link already sent.
- **VAPID private key** is an edge function secret only. Rotating it invalidates every existing push subscription, and browsers have to subscribe again.
- **CI secrets** (listed in [deployment.md](deployment.md#secrets)) are GitHub Actions secrets, scoped as narrowly as the providers allow. Fork PRs do not receive them.
- **If a secret leaks**, rotate it first, then investigate. Report leaks in this repository through private vulnerability reporting.
