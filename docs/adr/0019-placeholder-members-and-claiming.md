# 19. Placeholder members and claiming them

- Status: accepted
- Date: 2026-11-13

## Context

Splitwise lets you add "Sam" to a group before Sam has an account, split with him straight away, and hand the history over when he signs up. In Potluck every person is a `profiles` row whose id is an `auth.users` id (`profiles_id_fkey`), and everything that names a person (splits, payers, settlements, members, activity, notifications, policies through `auth.uid()`) points at that id. A person without an auth user could not exist, and the id of a future account cannot be known in advance: Supabase Auth picks it at sign up.

## Decision

- **A placeholder is a profile without an auth user.** `profiles.is_placeholder` marks it. `profiles_id_fkey` is replaced by two triggers that keep its meaning for real people: inserting a non-placeholder profile needs a matching `auth.users` row, and deleting an auth user deletes its profile. Nothing else changes for real accounts. A placeholder can never sign in (there is no auth user to sign in as) and is never `auth.uid()`, so `my_group_ids()`, `require_user()` and every own-row policy stay correct without edits.
- **It is an ordinary member.** A placeholder has a `group_members` row (role `member` only; a trigger refuses admin and owner), so it can pay, be in a split, be paid, have a balance and be read by group mates through the existing policies. The money rules apply unchanged: lock order, departed members, archived groups. It belongs to exactly one group; adding the same person to two groups makes two placeholders, both claimable.
- **Its private details live in `public.placeholders`.** One row per placeholder: group, optional email, who added it, invite and reminder times. Members read everything but the email (they see `email_hint`, masked); only RPCs read the address.
- **What it never does.** No push and no inbox: a before insert trigger on `notifications` drops every row for a placeholder except `member.added`, which becomes the invite email (sent through the [ADR 11](0011-notification-prefs-and-email.md) outbox to the placeholder's email, with the claim link). One reminder at most (`remind_placeholder`). No RSVPs, availability requests, best time gaps, friendships, 1:1 groups, ownership or admin role.
- **Claiming rewrites the id.** Sam can claim through his claim link (a `group_invites` row with `placeholder_id`, bound to the placeholder's email when there is one) or automatically when an account verifies an email that matches. The account's email must be verified in both cases. `private.claim_placeholder(placeholder, account)` takes the group row `for no key update` first (so no money write, which share-locks that row, runs at the same time), refuses if the account is already in the group, ever was, or is blocked by someone there (`placeholder_claim_conflict`, `blocked`), then updates every column that has a foreign key to `profiles(id)` (found in the catalog, so tables added later are covered), the user ids inside `activity.data`, notification payloads, `groups.default_split`, recurring templates and `expense_items.user_ids`, befriends the group, logs `member.claimed`, and deletes the placeholder profile. Triggers that would read the rewrite as an edit (expense activity and notifications, `updated_at`, the archived guard) return early while `potluck.claiming` is on. Amounts never change, so every balance moves to the account exactly as it was. Claiming works in archived groups: it changes who a balance belongs to, not the balance.
- **Friends are explicit too.** `friend_invites` gives everyone a reusable personal link plus single-use links bound to an email; `accept_friend_invite` makes the friendship (refused while either side blocks the other). `remove_friend` and `block_user` are RPCs because each changes both directions of `friendships` at once.
- **Two more anon RPCs**: `invite_preview_v2` (the group preview plus the saved seat's first name and email hint) and `friend_invite_preview` (inviter's first name and avatar). The code is the credential, as for `invite_preview` ([ADR 4](0004-security-definer-rpcs-for-multi-row-writes.md)).

## Consequences

- Any new table or column that stores a person's id must be a foreign key to `profiles(id)` (then claiming follows it for free) or be added to `private.claim_placeholder` (jsonb or arrays). A unique key that includes a user id is safe because the account is refused when it already appears in the group; a table keyed on the user alone (prefs, tokens) must be excluded there.
- A trigger added to a table that holds user ids sees the rewrite as an update. If it logs, notifies or guards, it should return early when `private.claiming()` is true.
- `profiles` no longer has a real foreign key to `auth.users`; the two triggers carry that rule. A hard delete of an auth user still removes the profile.
- Anyone who can add people to a group can make the app email an address once, plus one reminder. Placeholders with an email are capped per person per day (`too_many_invites`), every email carries the ADR 11 unsubscribe links, and the address is never shown to other members.
- Claiming is one transaction over every table that names the placeholder. It is cheap for the size of a group's ledger, and it runs inside sign up when the email matches, so it swallows its own errors there (the account is created; the seat stays unclaimed and the link still works).
