# 11. Notification settings per category, email from the database

- Status: accepted
- Date: 2026-11-13

## Context

Every notification went to the inbox and to every web push device, with one on/off switch per device. Splitwise lets people choose, per kind of event, whether they get a push and whether they get an email, sends a monthly summary, and puts a one-click unsubscribe in every email. Potluck has no email sender yet (no domain or provider), several branches are adding notification types at the same time, and the backend is Postgres plus a few edge functions with no queue service. Database hooks reach edge functions through `pg_net`, which gives up after 5 seconds.

## Decision

- **Settings are per category, not per type.** `private.notification_categories` holds one row per setting people see (new expenses, edits and deletions, payments, comments, groups, plans, reminders, monthly summary) with its push and email defaults and which channels it supports. `private.notification_types` maps each notification type to a category. A new type is one insert there; a type with no row is pushed and never emailed, so forgetting the row is noisy rather than silent. The settle up work's `settlement.updated`, `settlement.deleted`, `settlement.restored` and `debt.reminder` (and `payment.*` spellings) are mapped already.
- **Only changes are stored.** `public.notification_prefs (user_id, category, push, email)` keeps what someone switched; null means the default, so changing a default later reaches everyone who never touched it. Clients read with `my_notification_prefs()` and write with `set_notification_pref()`; there are no direct writes.
- **The inbox always gets everything,** the monthly summary card included, so unsubscribing from any email (the summary's too) keeps the inbox as it was and the unsubscribe page can truthfully say the inbox is not affected. A before insert trigger on `notifications` stores the routing decision in `notifications.channels` (`push`, `email`). The push hook only calls `notify` when `push` is in it.
- **Email is a flag plus a sender.** `app_config.email_notifications` starts false, and while it is false nothing is routed to email. Turning email on is configuration only: set `RESEND_API_KEY` and `EMAIL_FROM` on the functions, then flip the flag. The sender sits behind a small interface in `supabase/functions/notify/sender.ts`, so another provider is one more branch.
- **Email leaves through an outbox, in batches, and is reported back.** Rows routed to email go into `private.email_outbox`. Every minute `email-notifications` waits until nothing new has arrived for a subject for 60 seconds, folds changes to one expense into a single email (nothing at all if it was added and deleted inside the hold), re-checks settings, and hands the rest to `notify` in batches of 50 (one `pg_net` call each, rows marked `sending`). `notify` answers at once and keeps working in the background (`EdgeRuntime.waitUntil`), sends each batch in one call to Resend's batch endpoint with the batch id as the idempotency key, retries rate limits and server errors with backoff (honoring `Retry-After`), then reports through `email_outbox_report` (service role only). A delivered batch is `sent`. A reported failure goes back to `pending` with a fresh batch and waits 2, 4, 8, 16 minutes; after 5 attempts it is `failed`. A batch nobody reported within 10 minutes (the function died) is sent again under the same batch id, so the provider drops a copy it already accepted, but only when exactly the same rows go out again; if any of them was dropped or folded in the meantime, the rest get a new batch and key. Resend answers 409 `invalid_idempotent_request` when a key it accepted comes back with a different body (the same emails rendered again): `notify` treats that batch as sent. A 409 for a key still in flight is retried. Rows not sent within a day are dropped.
- **Unsubscribe links are signed in the database and need a click.** The token is `<user id>.<category or all>.<HMAC>` with a key generated into `private.signing_keys` by the migration; it never leaves Postgres. `public.email_unsubscribe(token, action)` is anon-callable: the token is the credential. `preview` changes nothing and returns the category and the account's masked address; `unsubscribe` turns email off; `undo` restores exactly the settings that unsubscribe changed, from a snapshot in `private.email_unsubscribe_undo`, taken only when some email the link covers was on and dropped when the person changes an email setting themselves. Without a snapshot, a one-category link turns that email on, and an `all` link changes nothing and says so, rather than resetting every setting to its default. The `/unsubscribe` page only previews on open and unsubscribes on a tap, because link scanners in mail gateways open every link. The one-click path for mail clients (RFC 8058) is a POST to the `unsubscribe` edge function, which scanners do not send.
- **The monthly summary is a notification.** On the first of the month `monthly-summary` writes one `summary.monthly` notification per person with a non-zero balance, built by `private.monthly_summary(uid, month)`. It is an inbox card, never a push, and an email when email is on.
- **`member.added` is groundwork.** The trigger notifies someone put into a group by another person, but today nobody can do that (joining is always through an invite, and 1:1 tabs are skipped). It starts firing when placeholder members land.

## Consequences

- New types from other branches follow the right setting as soon as they land. Anything else needs its row, a `describe.ts` case, push copy in `message.ts` and, optionally, email copy in `email.ts` (unknown types get a generic email).
- Settings are account-wide. The per-device push switch still decides whether a device is subscribed at all; the settings screen dims the push column while this device is not.
- Email copy lives in the edge function in English, like push copy; it does not go through `packages/i18n`.
- Delivery is at least once. A batch whose report is lost and is re-sent after the provider's idempotency window (24 hours for Resend) would be delivered twice; the one-day drop keeps that window short.
- A second anon-callable RPC widens the public surface. It only ever reads or changes the email settings of the person the token was signed for, shows their address masked, and a bad token raises `invalid_unsubscribe_link`.
- Requiring a tap on the web page costs one click for people whose mail client has no unsubscribe button; in exchange a scanner opening the link never unsubscribes anyone.
- The every-minute job writes a `cron.job_run_details` row per run even while email is off.
- Rotating the signing key (delete the row and insert a new one) breaks every unsubscribe link already sent, which is acceptable for a leak but should not be done casually.
