# 18. Export, backup format and import mapping

- Status: accepted
- Date: 2026-11-13

## Context

Splitwise exports a group or a friend as a spreadsheet for free and sells a JSON backup with Pro. People moving to Potluck want their Splitwise history in, and everyone wants their data out in a form a spreadsheet and a future import can read. Potluck already exported one group's expenses as CSV, but without payments, without what each person paid, and with nothing that tied the file back to the balances. Since ADR 12 an expense can have several payers, be a refund and carry line items, so a file that only lists shares can no longer be read back.

Splitwise's export (verified against real files shared in open source importers) is: Date, Description, Category, Cost, Currency, then one column per person holding what the row did to them (paid minus share, positive means they are owed); payments have the category "Payment" (translated); a negative cost is money that came back; one "Total balance" line per currency closes the file. It never says who paid what, only the net per person, and never converts currencies. Opened and saved again in a spreadsheet, dates come back as 3/1/26 or 01/03/2026.

A first version wrote each imported row through `private.save_expense`. A 5,000 row file took longer than PostgREST's 8 second statement timeout.

## Decision

- **One spreadsheet format for every export** (core `ledgerCsv`): group, everything, and one friend. Fixed columns (date, group, type, description, category, amount, currency, rate, group currency, amount in group currency, paid by), then per person "paid", "share" and "balance", then notes and items. Refunds are negative in amount, paid and share. A payment is "paid" by the payer and is the "share" of whoever got it. The balance columns come from core `expenseEffect` (convert once, spread twice), so each column sums to that person's balance to the cent, and a Balance row per group says so. A friend export keeps only the two people, names everyone else (people who left included) by name, and adds "Between you and ..." from the pairwise rule (`pairEffect`).
- **Column names follow the app's language**; the reader takes the current language and English. Payments are dated on the UTC day they were recorded, the day their rate is from.
- **The JSON backup is a database function** (`export_my_data()`), one consistent snapshot of every group the caller is in (archived ones too): members, expenses with payers, splits, items and comments (deleted expenses and payments included and marked, deleted comments left out), payments, recurring templates, plans with RSVPs, availability and comments, the profile, friends and the name of everyone mentioned. Format `potluck-backup`, `version: 1`, documented field by field in [backup-format.md](../backup-format.md) and pinned in code by core `backupSchema`. Adding a field keeps the version; renaming, removing or changing meaning bumps it.
- **Import is planned on the client and written in one transaction.** Core reads the file (`readImportFile`: Potluck's format by its header, Splitwise's by its shape, any language, ISO or spreadsheet dates with month or day first detected and switchable), the screen matches each person in the file to a member (guessed by name, always editable; two names may be one person; someone who left is shown as such; anyone can be "left out", which leaves out their rows), and core `planImport` turns rows into exact splits with explicit payers. Nothing is written until the person presses Import.
- **Every imported row carries its rate.** Rows in another currency take, in order: the Rate column of a Potluck file written in the same group currency (so a round trip is exact even if stored rates change), Potluck's stored rate for the day (the `private.fx_rate` lookup, done in core as `rateOnDay` from the stored history), or a rate the person types. Without one, the rows wait or are left out. The preview converts every row with the same rate, so "Balances after the import" is what the group will show. This is the one write where a client sends a rate: the rate is the importer's own data, and it is stored on the row like any other.
- **A rate a row brings is bounded.** Its currency must be one Potluck has stored rates for (the same table `save_expense` converts with), it must lie between a fifth and five times the nearest stored rate for the pair, any day (`RATE_BAND` in core, the same numbers in SQL), and no row may come to more than 100,000,000,000 minor units in the group currency. A rate outside the band, or one with no stored rate to compare with, goes in only with `fx_rate_confirmed`, which the app sends after the person ticks "This rate is right" under a warning; the amount cap holds even then. The screen keeps a typed rate as the exact text typed and applies it on leaving the field, Enter or "Use this rate".
- **Splitwise rows are rebuilt from their nets** (`fromNets`): everyone ahead paid, everyone behind owed their part, and whatever the cost leaves over is the payers' own share, spread equally among them. A negative cost is a refund, rebuilt from the flipped nets. One payer comes back exactly; "two paid, all split equally" comes back exactly; anything else keeps every person's balance exactly while the payer split may differ from the original. Rows that move no money are left out and counted.
- **`import_expenses` checks and writes as sets.** It locks the group row, checks membership and that the group is not archived, parses every row once into unlogged working tables in `private` (keyed by a run id, emptied before it returns; hash joins forced, since they never have statistics), finds the first failing row with the checks `save_expense` makes for an exact split with payers (description, amount, currency, payers valid, distinct, adding up and members, split valid, distinct, adding up and members, a rate for the day) and `settle_up` makes for a payment (two different current members), then inserts all expenses, payers, splits and payments in one statement each. A failure raises the same code `save_expense` would, with `import_row:<n>` in the hint, before anything is written. A 5,000 row file takes about 1.5 seconds through PostgREST locally, commit included. Imported rows also skip the activity, notification and lone payer triggers through WHEN clauses (the hold triggers stay as the safety net).
- **Up to 5,000 rows are one all or nothing import.** Requests carry at most 2,000 rows; a larger import is sent ahead with `import_stage(batch_id, group_id, rows)` into `private.import_rows` and written by the `import_expenses` call that names the batch. A longer file (up to 50,000 rows) goes in as several imports, one after another; the screen says so before, and if one fails, says how much went in, refreshes the balances and ticks "leave out the rows already here", so trying again does not double them. Staged parts nobody finished go after an hour (`purge-import-batches`, every 15 minutes), and nobody keeps more than three.
- **Duplicates are flagged, not refused.** The activity entry stores a fingerprint (SHA-256) of the file, so the same file again is named; rows matching an expense (day, amount, currency, description) or payment (day, amount, currency, people) already in the group are counted and can be left out.
- **One activity entry, no per row notifications.** While an import runs, `potluck.importing` holds the group id for the transaction; two before insert triggers drop the activity rows and notifications (including the expense notifications written at commit) it would cause, and the function logs one `expenses.imported` entry with the counts, source and fingerprint. Imported expenses therefore have no "added" history line; the detail page falls back to "Added by" from the row.

## Consequences

- The import path repeats `save_expense`'s checks in set form. A rule added to `save_expense` (a new column, a new limit) must be added to `import_expenses` too; `supabase/tests/20_export_import.test.sql` tests each check.
- Splitwise imports reproduce balances exactly but not always who paid which part of a several-payer bill; the file does not say. Items, receipts and comments do not come over from Splitwise, and the Potluck re-import keeps payers, shares and rates but not line items (they stay readable in the Items column).
- People who left cannot be given new rows (nothing may move a former member's balance); their rows are left out or wait until they rejoin.
- A file longer than 5,000 rows is not atomic as a whole: each part of 5,000 is.
- New writers of `activity` or `notifications` that run inside an import are held back too; a future bulk write that wants its own entries must not set `potluck.importing`.
- The format is a contract: the CSV header, the backup fields and the import row shape are tested in core, and changing them means updating the reader, `backupSchema`, backup-format.md and this record.
