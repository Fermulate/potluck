# 13. Export, backup format and import mapping

- Status: accepted
- Date: 2026-11-13

## Context

Splitwise exports a group or a friend as a spreadsheet for free and sells a JSON backup with Pro. People moving to Potluck want their Splitwise history in, and everyone wants their data out in a form a spreadsheet and a future import can read. Potluck already exported one group's expenses as CSV, but without payments, without what each person paid, and with nothing that tied the file back to the balances. Since ADR 12 an expense can have several payers, be a refund and carry line items, so a file that only lists shares can no longer be read back.

Splitwise's export (verified against real files shared in open source importers) is: Date, Description, Category, Cost, Currency, then one column per person holding what the row did to them (paid minus share, positive means they are owed); payments have the category "Payment" (translated); one "Total balance" line per currency closes the file. It never says who paid what, only the net per person, and never converts currencies.

## Decision

- **One spreadsheet format for every export** (core `ledgerCsv`): group, everything, and one friend. Fixed columns (date, group, type, description, category, amount, currency, rate, group currency, amount in group currency, paid by), then per person "paid", "share" and "balance", then notes and items. Refunds are negative in amount, paid and share. A payment is "paid" by the payer and is the "share" of whoever got it. The balance columns come from core `expenseEffect` (convert once, spread twice), so each column sums to that person's balance to the cent, and a Balance row per group says so. A friend export keeps only the two people and adds "Between you and ..." from the pairwise rule (`pairEffect`), summing to what the two owe each other in each group.
- **Column names follow the app's language**; the reader takes the current language and English. Payments are dated on the UTC day they were recorded, the day their rate is from, so a re-import converts at the same rate.
- **The JSON backup is a database function** (`export_my_data()`), one consistent snapshot of every group the caller is in (archived ones too): members, expenses with payers, splits, items and comments (deleted expenses and payments included and marked, deleted comments left out), payments, recurring templates, plans with RSVPs, availability and comments, the profile, friends and the name of everyone mentioned. Format `potluck-backup`, `version: 1`, documented field by field in [backup-format.md](../backup-format.md) and pinned in code by core `backupSchema`. Rates and weights are decimal text, money is integer minor units. Adding a field keeps the version; renaming, removing or changing meaning bumps it.
- **Import is planned on the client and written in one call.** Core reads the file (`readImportFile`: Potluck's format by its header, Splitwise's by its shape, any language), the screen matches each person in the file to a current member (guessed by name, always editable; two names may be one person), and core `planImport` turns rows into exact splits with explicit payers, shows the resulting balances and checks them against the file's own total lines. Nothing is written until the person presses Import.
- **Splitwise rows are rebuilt from their nets** (`fromNets`): everyone ahead paid, everyone behind owed their part, and whatever the cost leaves over is the payers' own share, spread equally among them. One payer comes back exactly; "two paid, all split equally" comes back exactly; anything else keeps every person's balance exactly while the payer split may differ from the original. Rows that move no money (everyone square, or a person paying themselves after matching) are left out and counted.
- **`import_expenses(group_id, rows, source)` is all or nothing.** It locks the group row, checks membership and that the group is not archived, then writes every expense through `private.save_expense` (the `create_expense_v2` path, so the same checks for members, people who left, sums and rates) and every payment like `settle_up` but between any two current members on the given day. Any failure rolls back the whole file and the error's hint names the row (`import_row:<n>`), which the screen maps back to the line in the file. At most 5000 rows per call.
- **One activity entry, no per row notifications.** While an import runs, `potluck.importing` holds the group id for the transaction; two new before insert triggers drop the activity rows and notifications (including the expense notifications written at commit) it would cause, and the function logs one `expenses.imported` entry with the counts. Imported expenses therefore have no "added" history line; the detail page falls back to "Added by" from the row.

## Consequences

- Splitwise imports reproduce balances exactly but not always who paid which part of a several-payer bill; the file does not say. Items, receipts, comments and edit history do not come over from Splitwise either, and the Potluck re-import keeps payers and shares but not line items (they stay readable in the Items column).
- Rows in another currency take Potluck's rate for their day. Days before the first stored rate cannot be imported; the preview says so before anything is written.
- New writers of `activity` or `notifications` that run inside an import are held back too; a future bulk write that wants its own entries must not set `potluck.importing`.
- The format is now a contract: the CSV header, the backup fields and the import row shape are tested in core, and changing them means updating the reader, `backupSchema`, backup-format.md and this record.
